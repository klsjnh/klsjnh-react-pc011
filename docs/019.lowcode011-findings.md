## 019.4 ⚠️ 实测踩坑（这些不是推测）

### ① 方法错配真会 500，不是 405
`GET` 端点用 `POST` 打 → **HTTP 500**，body 是 `HttpRequestMethodNotSupportedException`：

```bash
POST /klsjnh/lowcode011/julyMetadata/v1/getById   → {"statusCode":500,"message":"internal server error",
  "errorMessage":"HttpRequestMethodNotSupportedException: Request method 'POST' is not supported"}
GET  /klsjnh/lowcode011/julyMetadata/v1/getById?id=none → {"statusCode":404,"message":"record not found, id=none"}
```

→ 前端**必须**用 `api.get(action, { id })`（信封解析在 `request.ts` 收口，业务层别自己判 `statusCode`）。

### ② Swagger 里响应 content-type 全是 `*/*` —— **运行时其实是 `application/json`**
实测响应头：

```
POST /klsjnh/system011/julyUser/v1/login  [application/json]  {"statusCode":401,"message":"wrong account or password",...}
```

→ **不能因为 `*/*` 就在前端写 `res.text()` 再手动 JSON.parse**，直接 `res.json()` 即可。
（这与 `013.api-contract.md` 里「Swagger 声明不可靠、以实际 HTTP 行为为准」是同一类问题。）

### ③ 服务端**不校验前端有没有传 id**，直接落库
实测 `insert` 传了 `id` 字段 → **HTTP 200、建了一条垃圾数据**（`total` 从 0 变 1）。
→ 前端**必须**在提交前把 `id` 从 body 里剔掉（编辑/新增共用表单时尤其危险）。

### ④ 菜单入口：配置里有、后端没给
把登录后的 `getUserMenuTree` 打出来（`loginByUserName` 拿 token）：
9 个根节点里**没有** lowcode011 / 元数据的任何节点；数据中心下也没有「业务建模」。
→ 想让它出现在侧边栏，得**先在「菜单管理」里建菜单**（或在后端 seed 里加），前端 `GLOBAL_MENUS` 改了也没用（`menuFromConfig:false`）。

## 019.5 相邻模块 `julyBusinessModeling` 的对照（**旧版字段模型**）

同样实测 `GET /v3/api-docs` 的 schema，与前端现有 types 对不上：

| 项 | 后端（新版） | 前端现状 |
|----|-------------|---------|
| 字段子项子表名 | `fieldData: JulyBusinessModelingFieldVo011[]` | ✅ 名字相同但**字段完全不同** |
| 字段子项结构 | `code` / `name` / `fieldType` / `length` / `notNull` / `defaultValue` | ❌ 前端是 `fieldCode/fieldName/columnName/dataType/isPrimaryKey/isNullable/isRequired` |
| `fieldType` 取值 | `id/status/create_by/update_by/create_time/update_time/string/int/float/date/boolean/text` | ❌ 前端 Select 是 `varchar/int/bigint/decimal/datetime/text/boolean` |
| 主表扩展字段 | `objectType` / `objectDescription` / `packageName` / `businessField` / `routerPath` | ❌ 前端完全没有 |
| 保存入参 | `insert` / `update` 两个 schema | ⚠️ 前端只传子集（多余的会被忽略，少的会缺） |

**执行类接口的入参与前端也不一致：**

| 接口 | 后端入参 schema | 前端传的 |
|------|----------------|---------|
| `probe` | `JulyBusinessModelingProbeVo011`：`dataSourceCode` + `sqlContent` + `objectName`(仅记录) | 只传前两个 |
| `executeSql` | `JulyBusinessModelingExecuteVo011`：`dataSourceId`/`dataSourceCode`、`modelId`/`modelCode`/`sqlContent` **三选一** | 当必填传 `dataSourceCode + sqlContent` |
| `executeSqlByPage` | 同上 + `pageIndex` / `pageSize`(**clamp [10,500]**) | 同 |
| `getModelData` | **`GET`，参数只有 `id`** | ❌ 前端 `api.post(...)` + 传 `modelCode` → **必然 500** |
| `getById` | **`GET`** | ❌ 前端 `api.post(...)` → **必然 500** |

实测证据（前端现写法 vs 正确写法）：

```
MODELING getById    (POST=前端现写法) → HTTP 500 HttpRequestMethodNotSupportedException
MODELING getById    (GET)             → HTTP 404 record not found, id=none
MODELING getModelData (POST=前端现写法) → HTTP 500
MODELING getModelData (GET)             → HTTP 404
AI  getById        (POST=前端现写法) → HTTP 500   ← ai011 同样问题
```

**响应结构差别（会直接显示成坏页面）：**

| 接口 | 后端返回 | 前端期望 |
|------|---------|---------|
| `probe` | `{ success, message, fieldData: [...] }` | ✗ 期望 `columns: [{name,type}]` |
| `executeSql` | `{ columns: string[], rows: object[] }` | ~ 基本可用（前端多读 `success`/`elapsedMs` 会拿到 undefined） |
| `executeSqlByPage` | `PageResult011MapStringObject`：`{pageIndex,pageSize,total,totalPages,rows}` | ~ `rows` 可用，`columns` 没有 |
| `getModelData` | `JulyBusinessModelingVo011`：**整个建模对象 + `metaData: { objectName, description, objectType, packageName, importField, url, fieldData[] }`** | ✗ 期望结果集 `{columns,rows}` |

> 前端 `ModelingFormModal.tsx` 的 SQL 调试 Tab 里「获取模型数据」按钮点下去，
> 按现写法在**真后端**上必然 500（POST 打 GET 端点）。
