## 011.铁律（不可越界）

### 011.提交时机

- **只有用户明确发出「提交」「推送」「push」指令时**，才能执行提交脚本
- **禁止主动提交** —— 完成编码不等于可以提交

### 013.提交前置检查

提交前必须完成以下三项，**缺一不可**：

- **编译通过** —— 任何编译错误即熔断，不允许提交
- **测试通过** —— 单元测试 / 集成测试全绿
- **接口与逻辑自测通过** —— 核心功能及新增接口必须实测验证

> 提交脚本在执行 `add` 之前，必须先自动校验上述检查，任意一项失败**直接熔断**。
> 具体命令（本语言的构建与测试命令）见**本项目编码标准**与**项目事实卡**。

### 015.Git 操作权限

- **只读及本地状态类操作**（`pull` / `status` / `diff` / `log` / `branch` / `checkout` / `switch`）—— 助手**可自主执行**
- **写操作**（`add` / `commit` / `push`）—— **必须且只能通过提交脚本**统一执行，**禁止直接使用原生 `git` 命令提交**

### 016.助手权限边界

- **可自主执行**：编译、运行测试、启动服务、接口自测、只读及分支切换类 Git 操作
- **高危操作需明确授权**：执行提交脚本、删除文件 / 分支、数据库 Destructive 变更（如 `DROP TABLE`、`DROP COLUMN`、`TRUNCATE`、无 `WHERE` 条件的 `UPDATE/DELETE` 及破坏性 Migration）
- **轻量变更豁免**：仅修补拼写、单行注释等微小改动，可合并至当前 Task 汇报，免除独立审批

### 017.执行环境（Windows / Linux）

助手执行命令**必须直接在本机执行，禁止使用沙箱**。跨平台通用铁律：

- **长命令一律脱钩执行** —— 编译 / 测试 / 构建等耗时命令，必须**后台运行 + 输出写日志文件**，再从文件读结果，**禁止让会话等待长输出**
- **路径与换行按平台处理** —— 路径分隔符、换行符（CRLF / LF）、大小写敏感性在 Windows 与 Linux 间**不通用**；脚本跨平台时必须显式处理
- **卡死进程先清理再重试** —— 不得在进程残留状态下强行重跑

| 操作 | Windows | Linux |
|------|---------|-------|
| 后台运行 | `start /B` · PowerShell `Start-Process` | `setsid nohup` |
| 查看进程 | `tasklist` · `netstat -ano` | `ps aux` · `lsof -i` |
| 终止进程 | `taskkill /F /PID` | `kill -9` / `sudo kill -9` |
| 路径分隔 | `\`（工具内多用 `/`） | `/` |

> **Git Bash 混合环境提示**：在 Windows 上用 POSIX Shell 时，部分系统命令可能缺失（如 `dirname`），必要时显式补 `PATH`。

## 013.需求沟通与标准开发流程（七步）

收到需求后，**严格按此流水线执行，不得跳步**：

```text
[Step 1] Log conversation    -> docs/{YYYY-MM-DD}-chat.md
   |
[Step 2] Analyze requirement -> docs/requirement011/ (raw requirement)
                             -> docs/requirement013/ (high-level design)
                             -> docs/requirement015/ (detailed design)
   |
[Step 3] Break down tasks    -> write docs/{YYYY-MM-DD}.md (Todo list); ASK USER TO CONFIRM
   |
[Step 4] User approval       -> implement todo items one by one
   |
[Step 5] Quality gate        -> build + test + API self-test (all three required)
   |
[Step 6] Report results      -> report self-test outcome and task status
   |
[Step 7] Commit              -> ONLY on explicit "commit / push" instruction from the user
```

**逐条说明**：

| 步 | 做什么 | 关键约束 |
|----|--------|----------|
| 1 | 记录对话 | 原始对话入 `docs/{YYYY-MM-DD}-chat.md`（**禁写凭据 / 内网 IP / 密钥**） |
| 2 | 分析需求 | 三档递进：原始需求 → 概要设计 → 详细设计，**同编号同主题贯穿** |
| 3 | 拆解任务 | 写入 `docs/{YYYY-MM-DD}.md`，**必须提示用户确认** |
| 4 | 用户批准 | 批准后才动手；按 Todo **逐项**开发 |
| 5 | 质量验证 | 编译 + 测试 + 接口自测，**缺一不可**（见 `§011 · 013` 提交前置检查） |
| 6 | 成果汇报 | 汇报自测结果与 Task 完成状态 |
| 7 | 执行提交 | **仅在用户明确发出「提交 / 推送 / push」指令时**才执行 |

**两条补充铁律**：

- **不跳层**：任何主题都**逐层**推进 —— 源（架构专题 或 业务需求）→ 技术方案 → 编码。**禁止跨层下放**；架构主题同样必须经「技术方案」层。
- **轻量变更豁免**：不改契约、不改路由、不改状态模型、不改公共组件签名的局部实现变更，**可不走技术方案层**，直接开发并在 `docs/{YYYY-MM-DD}.md` 记录。判定标准只有一条 —— **是否触碰对外契约**：触碰必走，不触碰可豁免。

## 016.编号规则（全局序列）

编号（`{编号}`）是**全项目共享的一支序列**，与所在目录**无绑定关系** —— 同一个号可以作目录名、主题文件名，也可以作文档内小节号。

- **分配规则（两条禁忌）**：从 `011` 起**递增分配**，**跳过含数字 `4` 的号**（`014 / 024 / 034 / 040–049 / 140–149 …`），并**跳过 `012`**；其余**连号不留空**
  - **跳 4 动因**：`014` 一类编号与「版本号 / 十进制小数」形近（易被读作 `01.4`），且 `01x` 段预留给骨架类常驻文档；此为体系约定，**可解释、不轻改**
- **序列取值**：`011 / 013 / 015 / 016 / 017 / 018 / 019 / 020 / 021 / 022 / 023 / 025 / …`
  - `011 / 013` 同时是**两个阶段目录的保留号**（`requirement011 / requirement013`），与全局序列同源 —— `012`（禁忌号）与 `014`（含 `4`）自然空出，**并非步长为 2**
- **不复用、不回收**：一个号一经分配即永久占用 —— 文件改名、移出、归档、撤销均**不释放**该号
- **文档内小节号（分层独立起编）**：**每一级各自**从 `011` 起，按**同一规则**递增（跳 `012` 与含 `4` 的号）；**同级内递增**，不跨级连续
  - **子节序列独立**，不占用父级序列 —— 故 **父级恒为连续序列、不会因嵌套而断档**
  - **重号是预期行为，不是冲突**：不同层级、不同父级下的同级子节**各自独立起编**，因此**同一编号必然在文档内多次出现**。示例：

    ```text
    ## 011.top-level structure A
    ### 011.first section under 011
    ### 013.second section under 011
    ## 013.top-level structure B
    ### 011.first section under 013      <- same number as above, NOT a conflict
    ```

    `### 011` 出现两次**完全合法** —— 两条序列各自从 `011` 起，互不相干。判重只发生在**同一父级的直接子节之间**。
  - **同级内禁止重号**：同一父级下的编号子节必须各自唯一
  - **跨节引用必须写全路径**：因重号为预期，**裸 `§011` 不可用**（多义）。引用一律写**从顶层到目标的完整编号路径**，用 `·` 连接，如 `§011 · 013`
  - **引用顶层节本身**（无子节路径可写）：号必带节名消歧，写作 `§编号.节名`（如 `§011.铁律`、`§018.代码先行审查`）；**纯号（`§011`）一律禁写**
  - **引言节不编号**：非序列成员的引言性小节（如「分层总览」「一句话定位」）**直接写标题、不带号** —— 避免与同级内容节重号
  - **编号只出现在 `##` / `###`（小节号）**：`docs/` 下的文档标题（`#`）一律为「号 — 名称」形式（如 `# 013 — 工程结构（总的）`），**禁止**把 `#` 层用作文档内的分节编号
  - **门牌例外**：项目根的 `Agent.md` 是**跨项目通用门牌**，不属于 `docs/` 编号序列，标题为「文件名 — 一句话定位」形式，**不编号**
- **漏号自查法（必做）**：任一小节序列必须满足「**跳过 `012` / 含 `4` 的号，其余连号不留空**」。批量核验：`grep -rn --include='*.md' -E '^#{2,3} [0-9]{3}\.' docs` 导出全部小节号（**不依赖 globstar**），**按父级分组**逐组比对是否连续（不可跨父级拉平看）
  - **Windows 备选**（Git Bash 缺命令时，见 §011 · 017）：`Get-ChildItem docs -Recurse -Filter *.md | Select-String -Pattern '^#{2,3} \d{3}\.'` - **常见误区 1**：以为「某号被顶层文件名占用就不能再作小节号」—— **错**。编号是**全项目共享序列**，同一号可同时是文件名与小节号
  - **常见误区 2**：以为「同一号在文档内出现两次是违规」—— **错**。各父级下的子节各自从 `011` 起编，重号是**设计结果**；只有**同一父级下**重号才违规
- **同一主题同编号贯穿**：`{编号}.topic-{主题}.md`（主题 kebab-case 英文）在 `requirement011 / 013 / 015` 三目录**同名**
- **编号 ≠ 层级（铁律）**：小节号写作 `013` / `015` **不代表**该文档已跨到 `requirement013` 层；层级**只由内容决定**

## 017.归档规则

- 每日工作结束后：精简工作日志记录至 `docs/{YYYY-MM-DD}.md`，原始对话整理至 `docs/{YYYY-MM-DD}-chat.md`
- 每日首个任务开始前：**必须**将历史日志归档至 `docs/archive011/`，保证 `docs/` 根路径仅存留当天文件
- **日志双轨声明**：WorkBuddy 运行时另有约定记忆目录 `.workbuddy/memory/{YYYY-MM-DD}.md`（运行时机制，AI 自动读写）。**两处并存、职责不同**：`.workbuddy/memory/` 是运行时工作记录（含临时路径 / 调试过程），`docs/{YYYY-MM-DD}.md` 是**可交付的精简日志**（归档对象）。归档动作**只作用于 `docs/` 下的日期文件**，不触碰 `.workbuddy/`。
- **常驻知识库禁止归档**：`011` / `013` / `015` / `016` / `017` / `019` / `020` / `021` / `infrastructure011/` / `requirement011` / `requirement013` / `requirement015`
  - 判定：**除日志类（`{YYYY-MM-DD}.md` / `{YYYY-MM-DD}-chat.md`）以外的所有编号文档与专题目录，一律常驻** —— 新增文档不必回改本条
- **归档是动作，不是愿望** —— 由 AI 在每个任务开始时**检查并执行**，不得只写在文档里当作愿景
- `{YYYY-MM-DD}-chat.md` **禁止写入凭据 / 内网 IP / 密钥 / token**（脱敏后再落盘）

## 018.代码先行审查

对于涉及**底层公共库修改、多模块联动或破坏性重构**的操作，在**动手前**必须先在对话中向用户提炼汇报：

- 设计思路
- 关键变更路径
- 潜在风险点

获得认可后再开始编码，**避免方向性误偏**。
