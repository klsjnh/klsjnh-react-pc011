# 015 — 项目信息（Project Info）

> 项目事实卡：定位 / 技术栈 / 骨架 / 构建与运行 / 当前能力。

## 011.Project Scope & Position

React 19 中后台**前端技术底座（PC 端）**，无历史包袱，供业务系统直接作为起点或参考样板。包含组织、用户、角色、权限（RBAC3）等核心管控能力。对外保持稳定契约：分层架构（`Page → Store → Service → API`）、统一 HTTP 响应信封接收、全局数据与权限状态管理。

- **端形态**：本工程为 **PC 端**（Ant Design）；移动端为**独立工程**，不混装 UI 库（见 [017.tech-debt-redlines §A5](../017.tech-debt-redlines.md)）
- **配套后端**：`klsjnh-java17-framework011`（DDD 分层）；契约以运行时 OpenAPI 为准，见 `013.api-contract.md`

## 016.Layering & Dependency Rules

```text
Page / Component ──► Hook（useTable / usePermission）
                        │
                        ├──► Store（Zustand: global state）
                        └──► Service（data transform / orchestration）
                                └──► API（physical request mapping）
                                        └──► request.ts（Axios instance + interceptors）
                                                └──► Backend
```

| 层 | 职责 | 可依赖 | 禁止 |
|----|------|--------|------|
| `types/` | 横切契约：DTO / VO / Store 接口 / 枚举常量 | 无 | 依赖任何运行时模块（纯类型） |
| `utils/` | 无 UI 的基础设施（`request.ts` / 树转换 / 日期格式化） | types | import 业务域 |
| `api/` | **物理请求映射**：一函数一端点，泛型返回类型 | utils / types | 写业务逻辑、做数据转换、碰 UI |
| `services/` | **业务逻辑**：数据转换（`listToTree`）、跨接口编排 | api / types | 碰 React、碰 store、碰 UI |
| `store/` | **全局状态**：认证 / 权限 / 主题 / 布局折叠（Zustand） | services / types | 存服务端列表数据（§A3） |
| `hooks/` | 逻辑复用：`useTable` 分页加载、`usePermission` 权限断言 | store / services / types | 含 JSX（纯逻辑用 `.ts`） |
| `components/` | 全局通用 UI（`common/`）与布局框架（`layout/`） | hooks / store / types | 写业务页面逻辑 |
| `pages/` | 页面视图：数据拉取与交互组装 | 全部 | 直连 `request.ts` 绕过 api/service |
| `router/` | 路由表 + 动态挂载 + 路由守卫 | pages / store / types | 含业务逻辑 |

**依赖箭头**：`pages → components → hooks → store/services → api → request`；`types` 被各层引用，**不反向依赖任何层**。

**三条硬约束**（对应 [017.tech-debt-redlines](../017.tech-debt-redlines.md)）：

1. **信封解析只在一处** —— `utils/request.ts`，各层不再判 `statusCode`（§C5）
2. **状态只有一套** —— Zustand，禁手写 pub/sub（§A1）
3. **服务端数据不进全局 store** —— 列表数据生命周期跟随页面（§A3）

## 017.Core Design Decisions

1. **契约不在文档中写死**：后端地址与 API 前缀**不固化在文档 / 常量里**，以运行时 OpenAPI 为唯一契约，落盘快照至 `docs/contracts/`。理由：多前缀并存（`/core011/v1` 与 `/klsjnh011/...`）的债应由契约统一治理，而不是给业务代码打补丁（见 [017.tech-debt-redlines §C1/C2](../017.tech-debt-redlines.md)）。
2. **类型按域分层**：`types/models/` 放后端实体对应 VO，`types/services/` 放请求出入参契约，**禁单文件堆积**（§B1）。
3. **字段名唯一真源是 OpenAPI**：前端类型字段名与快照**逐字一致**，不做「前端更顺眼」的改名（§B2/C3）。
4. **日期格式后端负责**：契约统一 `yyyy-MM-dd HH:mm:ss`；前端只做展示层格式化，**不做 `T` 替换补丁**（§C4）。
5. **CRUD 收敛为工厂**：`useCrudTable` / `createCrudStore` 统一列表分页与增删改；能力不足**扩展工厂**，不在业务域复制粘贴（§A4）。
6. **路由是路由表**：路由 key = 页面文件名 = 菜单 key，**三者同名**；动态路由由后端菜单树驱动；**禁止别名映射表与 `/*` 通配分发**（§A2）。
7. **门禁随提交入口强制**：`tsc --noEmit` → ESLint → 规范检查脚本，随 `script011.sh` 前置执行；**不使用 git hooks**（与后端口径一致，见 [016.coding-standards §14](../016.coding-standards.md)）。

## 018.构建与运行

```bash
pnpm dev              # 开发服务器（Vite，端口见 .env.development）
pnpm build            # tsc --noEmit && vite build
pnpm preview          # 预览构建产物
pnpm lint             # ESLint 检查

./script011.sh gate       # 门禁：tsc --noEmit + ESLint + 规范检查
./script011.sh            # gate → 版本号自增 → commit（ver 0.0.N）→ push
./script011.sh build011   # 生产构建
./script011.sh start011   # 启动开发服务器
```

- **环境变量**：开发配置入 `.env.development`；本机私有覆盖入 `.env.local`（不入库）
- **代理**：Vite 代理路径**依据运行时 OpenAPI 的实际前缀**配置，不在文档中固化（见 [017.tech-debt-redlines](017.tech-debt-redlines.md) §C2）
- **前置**：Node 18+ · pnpm · git 仓库已 init 且配置 remote
