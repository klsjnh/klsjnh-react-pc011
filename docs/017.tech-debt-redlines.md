# 017 — 技术债红线（Tech Debt Redlines）

> **定位**：本项目的**禁止式约束清单** —— 把已知的、历史上真实发生过的技术债，固化为「不许再犯」的判定式条款。
> **执法方式**：每条规定标注强制手段 —— 【门禁】`tools/check-klsjnh-react-standards.mjs` 自动拦截 · 【TS】`tsc --noEmit` 类型系统拦截 · 【API】`ObjectStoragePort` 级接口约束 · 【评审】人工 / AI 评审项。
> **修订**：新增红线必须先说明**它堵的是哪一类真实问题**（问题 → 条款 → 强制手段），禁止写入凭空假设的规则。

---

## 011.债源档案（为什么要写这份文档）

本体系以 `klsjnh-react-java17-dev011/013` 为参考实现。参考实现在**工程实践上是对的**（垂直切片、约定大于配置、Mock 与真接口同源、Toast 金标准都很有价值），但在演进中积累了五类可识别的债。本体系在设计期就逐条封堵，**不背负这些债**。

| 债类 | 表现 | 后果 |
|------|------|------|
| **A 架构债** | 状态机制两套并存；路由绕开 Router 路由表；CRUD store 两套；移动端与 PC 端混装同一工程 | 每加一个页面要同时改 3~4 处硬编码；切换端形态要重构 |
| **B 类型债** | 全量类型堆单文件；同字段多命名；可选性失控；无代际后缀规范 | 类型约束失效，字段名靠背 |
| **C 契约债** | URL 多前缀并存；契约快照散落多份且位置漂移；字段名靠人工对齐；日期格式前端打补丁 | 联调必踩坑，补丁层层叠加 |
| **D 门禁债** | 有规则无检查；提交入口无 gate；`tsc` 不在提交前；无 ESLint | 规则靠自觉，规则越多越贬值 |
| **E 文档债** | 两套命名并存；编号语义冲突；缺双阶段目录；缺归档规则；无编号台账 | AI 无法判定设计阶段，跨仓引用错位 |

**根因**：规则写了但**没有执法载体**，且**同一件事有两个家**（两套状态、两套 store、两套前缀、两套文档命名）。

## 013.架构红线

### A1 状态机制唯一【评审 + 门禁】

- **全局状态只用 zustand**（含 `persist` 中间件做持久化）。
- **禁止手写 pub/sub / listener / 自建 store**（参考实现的 `userStore` 手写 `listeners: Set` + `emit` 属禁用形态）。
- **禁止多套状态机制并存**：不得出现「认证态手写、业务态 zustand」这类分裂。
- 允许的例外：**React 局部状态**（`useState` / `useReducer`）用于组件内部控制；**服务端数据**不进全局 store（见 A3）。

```ts
// ✅ 允许：zustand + persist
export const useAuthStore = create<AuthState>()(
  persist(
    (set) => ({
      token: '',
      user: null,
      setAuth: (token, user) => set({ token, user }),
      clearAuth: () => set({ token: '', user: null }),
    }),
    { name: 'klsjnh_react011_auth' },
  ),
)

// ❌ 禁止：手写订阅
const listeners = new Set<() => void>()
function emit() { listeners.forEach(fn => fn()) }
```

### A2 路由是路由表，不是字符串映射【评审 + 门禁】

- **禁止**用一张硬编码 key 白名单 + 别名表（参考实现的 `pageRoutes.ts` 形态）来兜路由。
- 路由定义**收敛到单一真源**（`src/router/`），动态路由由后端菜单树驱动或本地路由表声明，**二选一但只选一个**。
- **禁止** `HashRouter` + `/*` 通配 + 组件内部再 `switch` 分发页面（等于绕过 Router）。
- **禁止**维护 `ALIAS` 别名映射：路由 key = 页面文件名 = 菜单 key，**三者同名，不加别名**。

### A3 服务端数据不进全局 store【评审】

- 列表 / 分页 / 详情等**服务端数据**由页面级或专用的数据 hook / store 管理，**生命周期跟随页面**。
- 全局 store 只放**真正的全局态**：认证、权限、主题、布局折叠。
- 理由：把列表数据塞全局 store 会导致「离开页面不释放、跨页面互相污染、刷新时机难对齐」。

### A4 CRUD 逻辑只写一次【评审 + 门禁】

- **统一走工厂函数**（`createCrudStore` 形态，或 `useCrudTable` hook）——**禁止**每个业务域手写一遍同样的 `fetchPage / insert / update / remove / reset`。
- 若工厂函数能力不足，**扩展工厂**，不要在业务域内复制粘贴后魔改。

### A5 端形态不混装【评审】

- PC 工程与移动工程**分离**，各自独立依赖（PC 用 `antd`，移动用 `antd-mobile`），**禁止同一工程同时引入两套 UI 库**。
- 共享的是**机制与类型**（通过 docs 与本文件约定），**不是 node_modules**。

## 015.类型红线

### B1 类型按域分层，禁单文件堆积【门禁】

```
src/types/
├── api.d.ts                 # 仅信封与分页：Response011<T> / PageQuery011 / PageResult011
├── common.ts                # 跨域基础类型与枚举
├── models/                  # 后端实体对应的 VO（按域一文件）
│   ├── julyUser.ts
│   ├── julyRole.ts
│   └── julyMenu.ts
└── services/                # 请求出入参契约（按域一文件）
    └── julyUser.ts          # JulyUserQuery011 / JulyUserSaveVo011
```

- **禁止**把所有域实体堆在一个 `types/index.ts`（参考实现 321 行单文件属禁用形态）。
- `types/index.ts` 若保留，**只做 barrel 转出**，不放实体定义。

### B2 一字段一名，禁别名【门禁】

- **禁止**同一语义字段出现多种拼写。以下为参考实现中的真实冲突，一律**禁止**：

| 禁用 | 统一为 |
|------|--------|
| `passWord` | `password` |
| `createDate` / `updateDate` | `createTime` / `updateTime`（与后端公共列一致） |
| `remark011` / `remark013` | `remark` |
| `version011` / `version013` | `version` |
| `taskCode` / `taskName`（对 `schedulerCode` / `schedulerName`） | 以**后端 Swagger 为准**，前后端同名字段同名 |

- 判定：**字段名唯一真源是运行时 OpenAPI**（见 `013.api-contract`）。前端类型字段名必须与之逐字一致，不做「前端更顺眼」的改名。

### B3 可选性必须精确【TS】

- 后端**必出**的字段**不得**标 `?`。参考实现中 `status?: string` 遍布所有实体属禁用形态。
- 只有**真正可能缺省**的字段才用 `?`；后端可能返回 `null` 的用 `| null`，**不用** `?` 糊过去。
- `strict: true` 必须开启，**禁止** `any`、禁止 `as any`、禁止 `@ts-ignore`（确需时用 `@ts-expect-error` + 原因注释，且必须评审通过）。

### B4 代际后缀统一【门禁】

- 与后端 `*Vo011` / `*Po` / `*Repository` 规范对齐，前端类型同样带代际标记：

| 类别 | 后缀 | 示例 |
|------|------|------|
| 传输载荷（入参/出参） | `*Vo011` | `JulyUserIdVo011`、`JulyUserSaveVo011` |
| 分页对（自带方向语义，例外） | `*Query011` / `*Result011` | `PageQuery011`、`PageResult011` |
| 统一响应信封 | `Response011` | `Response011<T>` |
| 实体 View Object | `*Vo011` | `JulyUserVo011` |
| 枚举 / 常量 | 语义名 + `011` | `Status011`、`HttpCodeEnum011` |

- **禁止**同类之间无后缀混用（参考实现 `JulyConfig`（无 011）与 `ModelInfo011` 并存属禁用形态）。

### B5 业务对象必带 `july` 前缀【门禁】

- 域实体及其**文件 / 目录 / 类型 / 函数**四种形态**必须带 `july` 前缀**，对齐后端 `JulyUser` / `july_user` / VO 目录 `julyuser/` / URL 段 `julyUser`。
- 完整规则（含三形态对照表与例外）见 [016.coding-standards §4](016.coding-standards.md)。
- **禁止**出现裸命名：`user.ts` / `UserVo011` / `getUserList` / `pages/system011/user/`。
- **禁止**把后端端点动词改写成前端习惯语序（`selectListByPage` ✗→ `getUserList`）；函数名逐字对齐端点，映射靠搜不靠记。
- **例外**：通用领域概念字段（`auth` 的 `user`）、框架级组件（`components/common/` 下的 `OrgTree.tsx` / `Permission.tsx`）、非 IAM 域（沿用各自后端实体前缀）。
- 判定：搜索 `src/` 下 `models|services|api|pages` 的业务对象文件，文件名不含 `july` 且对应后端 `july_*` 表 → 违规。

### B6 禁止缩写命名【门禁】

- 目录 / 文件 / 变量名**一律用完整词**：`common` 不写 `comm`、`configuration` 不写 `conf`、`component` 不写 `comp`、`message` 不写 `msg`、`request` 不写 `req`、`response` 不写 `res`（**注意**：`res` / `req` 作**函数参数名**是业界惯例，可保留；作**文件名 / 目录名**禁用）。
- **例外**（业界已固化）：`api` / `utils` / `props` / `ref` / `src` / `env` / `config` / `env`。
- 判定：目录名长度 ≤ 4 且不在例外表 → 人工复核是否为缩写。
- **动因**：缩写靠约定记忆维持（`comm` 是 `common` 还是 `command`？），新人 / AI 都要额外推断；完整词自解释、可被 grep 精确命中。**目录名是长期资产。**

## 016.契约红线

### C1 契约唯一真源是运行时 OpenAPI【评审 + 门禁】

- **禁止**在文档、常量、注释中写死 API 前缀或字段清单当作契约。
- 契约来源 = **运行中的后端 OpenAPI**：`{backend}/v3/api-docs`（JSON）或 `{backend}/doc.html`（UI）。
- 每轮联调前**重新拉取**并落盘至 `docs/contracts/{YYYY-MM-DD}-openapi.json`，作为**可审计快照**。
- **禁止**保留多份散落的契约摘录文件（参考实现的 `swagger-联调摘录-*.md` 属禁用形态）。
- 详细流程见 `013.api-contract.md`。

### C2 禁止在文档中固化 URL 前缀【评审】

- 参考实现同时存在 `/core011/v1/...`、`/klsjnh011/{域}/...`、`/klsjnh011/dataservice011/...` 三种前缀，且带补丁说明 —— **属禁用形态**。
- 本体系**不预设前缀**：以 OpenAPI 的 `servers` 与 `paths` 为唯一依据。代理配置从环境变量读取，**不硬编码前缀**。
- Vite 代理**按 OpenAPI 实际路径前缀**配置；新增前缀时同步代理，而不是给业务代码打补丁。

### C3 字段名靠契约，不靠人工对齐【评审】

- **禁止**「人工核对 Swagger 后手改前端字段名」作为长期机制。
- 契约快照落盘后，字段名以快照为据**逐字对齐**；发现不一致 → 改前端类型，**不改后端**（除非契约本身要改，走 `requirement013`）。
- 后续可引入类型生成（`openapi-typescript`）。**当前阶段不引入**，先建立「快照 + 逐字对齐」的纪律。

### C4 日期格式后端负责，前端不打补丁【评审】

- 契约格式统一 **`yyyy-MM-dd HH:mm:ss`**（空格分隔，非 ISO `T` 格式）。
- **禁止**在前端把 `T` 替换为空格来「看起来正常」（参考实现的 `formatDateTime` 兜底属**临时**措施，不是机制）。
- 若后端返回带 `T` 的 ISO，**归类为后端契约缺陷**，记入 `docs/{YYYY-MM-DD}.md` 并推动后端修（Jackson 对 `LocalDateTime` 配 `@JsonFormat`）。
- 前端 `formatDateTime` 只做**展示层格式化**（如 `YYYY-MM-DD` 截断、相对时间），**不做格式修复**。

### C5 信封解析收口一处【评审 + 门禁】

- 信封六键（`statusCode` / `message` / `errorMessage` / `timestamp` / `traceId` / `data`）解析**只在请求客户端一处**（`src/utils/request.ts`）。
- **禁止**业务层再判一次 `statusCode === 200`，**禁止**在页面里重复写「响应缺字段」的校验。
- 401 处理也收口一处：客户端统一清 token + 跳登录，**禁止**各业务域各写一套。

## 017.门禁红线

### D1 规则必须有执法载体【评审】

- 写入 `016.coding-standards` 的每条规则，**必须在门禁脚本或 ESLint 中有对应实现**（标注 rule id）。
- 无法自动化的规则，**必须标注【评审】**，且分类为「靠人/靠 AI 评审」，不得含糊为「大家都应该遵守」。

### D2 门禁随提交入口强制执行【评审】

- 提交**唯一入口是 `script011.sh`**：`gate → 版本号自增 → commit → push`。
- **禁止**直接 `git commit` / `git push` 绕过（与后端 java17 口径一致）。
- 单独跑门禁：`./script011.sh gate`。门禁失败**不允许提交**。
- **禁止**使用 git hooks（门禁在提交入口内前置执行，不用 hook 双重实现）。

### D3 `tsc --noEmit` 必须在 gate 内【门禁】

- 类型检查是**提交前动作**，不能只在 `pnpm build` 里。
- 门禁顺序：**`tsc --noEmit` → ESLint → 规范检查脚本 → 构建校验**。

### D4 ESLint 必须存在且规则可解释【门禁】

- 必须有 ESLint 配置（flat config），且**每条自定义规则都对应 `015` 的编号章节**。
- **禁止**引入「默认推荐全集」而不加说明 —— 规则集是要能说清「为什么禁这条」的。

### D5 AST 类检查环境异常即失败【评审】

- 若使用 tree-sitter / TS AST 类检查，**环境缺失时门禁直接失败，不允许降级跳过**（同后端口径）。
- 理由：可跳过的检查等于没有检查。

## 018.文档红线

### E1 编号严格跳 4，且全局唯一序列【评审】

- 编号从 `011` 递增，**跳过 `012` 与所有含 `4` 的号**（`014 / 024 / 034 / 040–049 / …`）。
- 「开发标准」落 **`016.coding-standards.md`**，**禁止**使用 `014.开发标准.md` 这一编号（参考工程用的 `014` 与本体系铁律冲突，属**已知冲突**，新体系裁决为**严格跳 4**）。
- 详见 [`011.agreements.md`](./011.agreements.md) §016。

### E2 同一件事只有一个家【评审】

| 事项 | 唯一归属 |
|------|----------|
| 提交纪律 / 权限边界 / 执行环境 / 开发流程 / 架构分层 / 命名总原则 | `Agent.md` |
| 文档体系 / 编号 / 归档 | `docs/011.agreements.md` |
| 项目事实（技术栈 / 构建 / 能力） | `docs/015.project-info.md` |
| 编码规则 + 门禁映射 | `docs/016.coding-standards.md` |
| 契约来源 + 信封 + 状态码 | `docs/013.api-contract.md` |
| 技术债红线 | `docs/017.tech-debt-redlines.md` |
| 架构专题（横切设计） | `docs/infrastructure011/` |
| 业务设计 / 技术方案 | `docs/requirement011/` · `docs/requirement013/` |

- **禁止**在两个文件里重复同一份内容（参考实现 `014.开发标准` 与 `013.项目架构` 对目录结构重复描述属**禁用形态**）。
- 需要互引时用**链接**，不复制正文。

### E3 设计推进不跳层【评审】

- 任何主题：源（`infrastructure011/` 或 `requirement011/`）→ `requirement013/` 技术方案 → 编码。
- **禁止**跨层下放；架构主题同样必须经 `requirement013`。
- 轻量变更（不触碰对外契约）可豁免，判定标准见 [`011.agreements.md`](./011.agreements.md) §015。

### E4 归档是动作，不是愿望【评审】

- **每日首个任务开始前**必须把历史日志归档至 `docs/archive011/`，保证 `docs/` 根只留当天文件。
- 该动作由 AI 在每个任务开始时**检查并执行**（当前无 automation 载体，**明确由 AI 承担**，不得只写在文档里当作愿景）。

### E5 无编号台账即无法协作【评审】

- 新主题分配编号前，**必须先查 `011.agreements.md` §017 台账**并登记。
- **禁止**自行选号（避免 `requirement011 / 013` 两侧不同号、或与他人主题撞号）。

## 019.红线速查（交给 AI 的门禁清单）

提交前逐条自查，任一条不通过即不得提交：

1. 状态只用 zustand？无手写 pub/sub？（A1）
2. 路由走路由表？无别名表 / 无 `/*` 通配分发？（A2）
3. 服务端数据没塞全局 store？（A3）
4. CRUD 走工厂，无复制粘贴？（A4）
5. 单工程只有一套 UI 库？（A5）
6. 类型按域分层，无单文件堆积？（B1）
7. 无字段别名（`passWord` / `createDate` / `remark011`）？（B2）
8. 无 `any` / `as any` / `@ts-ignore`？可选性精确？（B3）
9. 类型带 `011` 代际后缀？（B4）
10. **业务对象带 `july` 前缀**（文件 / 目录 / 类型 / 函数四形态一致）？（B5）
11. **API 函数名逐字对齐后端端点动词**（`selectListByPage` / `logicDelete`，未改语序）？（B5）
12. **无缩写命名**（`common` 未写成 `comm`）？（B6）
13. 契约取自运行时 OpenAPI 快照？无写死前缀？（C1 / C2）
14. 字段名与快照逐字一致？（C3）
15. 日期格式后端负责，前端无 `T` 替换补丁？（C4）
16. 信封解析收口在 `request.ts`？（C5）
17. `tsc --noEmit` 通过？（D3）
18. ESLint 通过？（D4）
19. 规范检查脚本通过？（D1 / D2）
20. 编码编号跳 4？（E1）
21. 同一内容只有一个家？（E2）
22. 触碰对外契约的变更走了 `requirement013`？（E3）
23. 历史日志已归档？（E4）
