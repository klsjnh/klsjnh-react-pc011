### 020.2.2 元数据设计器（039 一期）—— 同前缀（4 个）

**这一组是 MetaDTO 口径**，与 020.2.1 的「一主三子」是**两套并存**的契约，别混用：

| # | action | 方法 | 前端 service 函数 | 说明 |
|---|--------|------|-------------------|------|
| 8 | `/julyMetadata/v1/listModels` | **GET** | `listMetadataModels()` | 无入参，回全量模型（后端内部固定 `pageSize=1000`） |
| 9 | `/julyMetadata/v1/load` | **GET** | `loadMetadataDto(objectName)` | 载入为 **MetaDTO**（`metaData` + 三子在**顶层**） |
| 10 | `/julyMetadata/v1/save` | POST | `saveMetadataDto(dto)` | 后端按 `objectName` 自判 insert / update，**前端不传 id** |
| 11 | `/julyMetadata/v1/previewDdl` | **GET** | `previewMetadataDdl(objectName)` | 回 `{ ddl }`；**与 publish 共用同一生成器** |

**MetaDTO vs 一主三子（键名差异，最容易踩）**：

| 子表 | 一主三子（038） | MetaDTO（039 一期） |
|------|----------------|---------------------|
| 字段 | `fieldCode / fieldName / fieldLength / requiredField` | `code / name / length / notNull` |
| 显示列 | `displayCode / displayName / param011` | `code / name / param011` |
| 服务 | `serviceCode / serviceName / serviceDescription` | `code / name / description` |
| 位置 | 三子挂在主表对象上 | 三子在**顶层**（与 `metaData` 平级） |

**DDL 生成规则**（源码 `MySqlMetadataDdlGenerator`，被 `previewDdl` 与 `publish` 共用）：

- 表名统一 **`lc_` 前缀** → `CREATE TABLE IF NOT EXISTS \`lc_<objectName>\``
- 首个 `id` 类型字段作主键；**一个都没有时自动补** `` `id` VARCHAR(33) NOT NULL COMMENT 'primary key' ``
- 类型映射：`id/status/create_by/update_by→VARCHAR(33|3)`、`date/create_time/update_time→DATETIME`、`int→INT`、`float→DECIMAL(18,4)`、`boolean→TINYINT(1)`、`text→TEXT`、其余→`VARCHAR(len||255)`，**上限 2000**
- 标识符白名单 `^[A-Za-z_][A-Za-z0-9_]{0,59}$`；非法标识符 / 未知类型 / 无字段 → **400**
- 表尾 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='<描述>'`（无分号）
- 补列走 `generateAddColumns` → `ALTER TABLE \`t\`\n  ADD COLUMN ...`，**只 ADD，永不 DROP / MODIFY / RENAME**

### 020.2.3 元数据发布 / 数据同步（039 二期，2026-09-17 上线）—— 同前缀（3 个）

| # | action | 方法 | 前端 service 函数 | 说明 |
|---|--------|------|-------------------|------|
| 12 | `/julyMetadata/v1/publish` | POST | `publishMetadata({objectName, migrateData, includeDeleted})` | **真正执行 DDL**；首次 CREATE，之后仅 ADD COLUMN |
| 13 | `/julyMetadata/v1/importStatus` | **GET** | `getMetadataImportStatus(objectName)` | 回 `{dataInitialized, physicalTable, publishStatus}` |
| 14 | `/julyMetadata/v1/importDataFromSql` | POST | `importMetadataDataFromSql({objectName, dataSourceCode, sqlCode, pageNum, pageSize, forceInit})` | 源 SQL 分页读 → 物理表 upsert |

**`publish` 的服务端行为**（源码 `JulyMetadataPublishUseCase`）：

1. 按 `objectName` 取聚合 → 表名 `lc_ + objectName`
2. 版本号 = `nextVersion(最新快照)`：**无快照 → `0.0.1`**，否则 patch 位 +1（**字符串递增，非整数**）
3. 表不存在 → `generateCreate`；表存在 → 只对**缺失列** `generateAddColumns`；**无缺失列 → ddl 为 `null`（无操作）**
4. 执行前受开关 **`krt.lowcode.ddl-execute.enabled`** 控制（`DatasourceDdlExecutor`，默认 false；开发环境 yml 已置 `true`）
   —— 关闭时抛 `IllegalStateException` → **400 `ddl execute disabled (krt.lowcode.ddl-execute.enabled=false)`**
5. 写快照 `july_metadata_version` + 推进主表 `publish_status / version / physical_table / backup_table`
6. 返回 `{objectName, version, publishStatus:"published", physicalTable, backupTable:null, ddl}`

**`importDataFromSql` 的服务端行为**（源码 `JulyMetadataDataSyncUseCase`）：

1. 先 `getByObjectName` → 对象不存在 **404 `record not found, id=<objectName>`**
2. 再取最新快照 → **未发布 → 400 `object not published: <objectName>`**
3. `dataSourceCode` 空 → 400；`sqlCode` 空 → 400
4. `pageNum` < 1 → 1；`pageSize` 缺省 100、**上限 500**
5. 源 SQL 走业务建模执行器（`BusinessModelingExecuteCommand.dataSourceCode + sqlContent`，方言分页）
6. 写入器 `JdbcTemplateMetadataDataWriter`：**大小写不敏感**匹配目标列，只写目标表**实际存在**的列；
   源里缺的平台列自动补默认值（`id`=UUID、`status`='1'、`dr`='0'、`create_time`/`update_time`=now），保证 NOT NULL 不阻塞导入
7. 返回 `{mode:init|sync, pageNum, pageSize, hasMore, nextPageNum, inserted, updated, unchanged, skipped, processed, dataInitialized}`
   —— ⚠️ **`updated` / `unchanged` / `skipped` 恒为 0**（源码写死），只有 `inserted`（= 本页处理行数）可信

> ⚠️ **命名陷阱**：`importDataFromSql` 的参数名叫 **`sqlCode`，实际语义是 SQL 文本**
> （后端把它直接喂给 `BusinessModelingExecuteCommand.sqlContent`）。前端 UI 标签已按「源 SQL」呈现。

## 020.3 B 档 · 契约错配（⚠️ 已修正的 5 处）

这 5 处接口**一直都在**，是前端调错了。方法错配在本项目后端表现为 **HTTP 500**（`HttpRequestMethodNotSupportedException`），**不是 405** —— 所以「看着像后端炸了」，实际是前端打错方法。

| # | 位置 | 修正前（错） | 修正后（对） | 症状 |
|---|------|-------------|-------------|------|
| 1 | `getModelingById` | `api.post(getById, {modelCode})` | `api.get(getById, {id})` | 打开已有模型必 500 |
| 2 | `getModelData` | `api.post(getModelData, {modelCode})` | `api.get(getModelData, {id})` | 「获取模型数据」必 500 |
| 3 | `probe` 消费形状 | 期望 `columns: [{name,type}]` | 消费 `fieldData: FieldVo011[]` | 探针结果页空白 |
| 4 | 输出嵌套层级 | `fieldData` 当顶层读 | `fieldData` 嵌在 `metaData` 下 | 「字段数」恒为 0 |
| 5 | 字段子项字段名 | `fieldCode/fieldName/columnName/dataType/...` | `code/name/fieldType/length/notNull/defaultValue` | 子表全空 / 提交被忽略 |

> **`FieldType011` 是两侧共用的类型枚举**（12 值：`id / status / create_by / update_by / create_time / update_time / string / int / float / date / boolean / text`）—— 这正是「建模 → 元数据」能无损搬运的前提。
> 前端把旧写法 `varchar/bigint/datetime/...` 全部换成了 `FieldType011` 口径（`FIELD_TYPE_011_OPTIONS`）。

### 020.4.3 占位的三条硬约束（写在这里防后人踩）

1. **状态是内存态**（`Map`），**刷新即重置** —— 这是占位实现的固有局限，不是 bug。
2. **绝不静默**：运行时页顶部常驻橙色 `Alert`「数据 CRUD 为前端占位实现（PENDING-BACKEND）」；设计器的发布菜单 / 开放 API 按钮带 `🧪` 标记 + 新建对象（无 `objectName`）时**禁用**。
3. **与真后端同构**：占位接口的入参 / 出参形状**照抄老项目 `metadata.ts` 的类型**（`OpenApiConfigResult` / `RuntimeMenuRow` …），后端补齐后**调用方零改动**。
4. **发布态一律取自真实 `importStatus`**：运行时页与设计器都**不再**从占位 Map 读发布态
   （`listModels` / `load` 里的 `publishStatus` 是后端硬编码假数据，见 §020.9 风险 1）。


**注意 MetaDTO 让桥更短了**：后端 `save`（039 一期）入参的 `fieldData` 键名与业务建模 `getModelData` 产物的 `fieldData` **完全同形**（`code / name / fieldType / length / notNull`）—— 理论上可直连 `getModelData` → `save`，无需经 038 的长键名转换。

| `url` | `routerPath` |
| `fieldData[].code / name / fieldType / length / notNull` | `fields[].fieldCode / fieldName / fieldType / fieldLength / requiredField` |

**页面入口（均按 `objectName` 用 query 传参）**：

| 来源 | 目标 | 路径 |
|------|------|------|
| 业务建模列表「元数据」 | 元数据列表（预置搜索） | `/lowcode011/JulyMetadata?objectName=xxx` |

## 020.9 未决 / 风险

| # | 项 | 说明 |
|---|----|------|
| 1 | **`listModels` / `load` 的 `publishStatus` / `version` 是假数据** | 两处均**硬编码** `'draft'` / `''`（`JulyMetadataDesignerUseCase` 源码，二期上线后**仍未读取**真列）。**唯一可信的发布态来源是 `importStatus`** —— 前端设计器页与运行时页均已改用它。 |
| 2 | **`publish` 的 `migrateData` / `includeDeleted` 是预留参数** | 源码注释写明「reserved for the data migration step」，**收而不用的迁移能力**：不会 rename 旧表、不会迁移数据，返回的 `backupTable` 恒为 `null`。UI 已明示，别当功能用。 |
| 3 | **`importDataFromSql` 的 `sqlCode` 实为 SQL 文本** | 后端把它直接传给 `BusinessModelingExecuteCommand.sqlContent`。命名误导，前端 UI 标签按「源 SQL」呈现。 |
| 4 | **数据同步计数三值恒 0** | `updated` / `unchanged` / `skipped` 在 `JulyMetadataDataSyncUseCase` 里**写死为 0**（写入器只返回处理行数）。前端只展示「写入 N 行」，不再宣称「更新 / 未变」。 |
| 5 | **`publish` 有真实副作用** | 会**真执行 DDL** 并写快照表 + 推进主表发布指针。受 `krt.lowcode.ddl-execute.enabled` 控制（默认 false，关闭时 400）。生产环境**开这个开关前务必确认**——它意味着任意 `objectName` 都能触发建表。 |
| 6 | **GET 缺必填 query 参一律 500** | `importStatus` / `load` / `previewDdl` / `getById` / `getByObjectName` 缺参 → **HTTP 500**（`MissingServletRequestParameterException` 未被映射为 400）。前端须自行保证传参。POST 端点的必填校验则是正常的 400。 |
| 7 | **两组口径并存** | 038「一主三子」（长键名）+ 039「MetaDTO」（短键名、三子顶层）同时有效。**同一处代码不得混用**；设计器页目前仍走 038 口径（已验收），MetaDTO 接口仅供新场景（如建模直通）。 |
| 8 | **枚举未展开** | `DisplayType011` / `ServiceObjectType011` / `ServiceParamType011` 后端 Swagger 未展开。运行时的「服务开关」判定同时认 `serviceCode`（insert/update/…）与 `objectType`（query/save/…），**无匹配行 = 视为开启**（与老项目 `enabled !== false` 一致） |
| 9 | **`displays` 无 `scene`** | 老项目 displays 带 `scene: list\|form\|query` 三态，新 VO **只有 `componentType` / `displayType`** —— 故运行时页派生规则改为「列表=displays、表单=fields 剔审计列、查询=前 4 个文本/状态列」，非等价移植 |
| 10 | **公共列不自动补** | 元数据保存时后端**不会**自动加 `id/status/create_by/...`（与建模侧 `replaceFields` 同款语义）→ 前端提交必须带全字段集。**例外**：`previewDdl` / `publish` 会在无 `id` 字段时自动补主键列。 |
